# 옵션 탐색: 자격증 기출문제 풀이 웹앱 — 구현 방식

기반 문서: `docs/prd/cert-exam-app.md` (APPROVED, Approach B "Ideal Architecture")

이 문서는 제품 방향(무엇을 만들지)이 아니라, 이미 확정된 방향을 **어떻게 구현할지**에 대한 옵션 비교다.

## 1. raw.md → questions.json 파싱 방식

`data/exam-questions/*/raw.md`는 pymupdf로 추출된 원문 텍스트로, 정답 문항이 굵은원문자(❶❷❸❹, U+2776-2779)로, 오답이 평범원문자(①②③④)로 명확히 구분되어 추출되는 것을 실제로 확인함.

| 옵션 | 장점 | 단점 |
|---|---|---|
| **정규식 기반 자동 파싱 (채택)** | 빠르고 비용 없음. 굵은원문자 유니코드 범위가 명확해서 정답 식별 정확도가 높음 | 줄바꿈으로 쪼개진 보기(예: `Ca2` / `+` 분리 케이스)는 후처리 규칙 보정 필요 |
| LLM 보조 파싱 | 줄바꿈/복잡한 서식에 강함 | 52개 파일(향후 더 늘어남) 기준 비용·시간 소요, 할루시네이션 위험 |
| 정규식 + 실패 문항만 LLM 보조 (하이브리드) | 정확도·비용 균형 | 초기 구현 복잡도 증가 — 지금 스코프엔 과함 |

**채택**: 정규식 기반 자동 파싱. PRD Next Steps에 이미 명시된 "회차별 랜덤 N문항 수동 대조 표본 검수"와 함께 적용해 정확도 검증.

## 2. OMR 그리드 스타일 답안지 UI

| 옵션 | 장점 | 단점 |
|---|---|---|
| **순수 CSS Grid/Flexbox (채택)** | 구현 빠름, 접근성(스크린리더) 기본 확보, 모바일 반응형을 breakpoint로 자연스럽게 처리 | 실제 OMR 카드만큼 정교한 시각 효과는 제한적 |
| Canvas/SVG 직접 그리기 | 시각적으로 더 정교한 OMR 재현 가능 | 터치/접근성 처리를 직접 구현해야 함 — "가볍게" 제약과 충돌 |
| 기존 UI 라이브러리(shadcn/radix RadioGroup 등) 재활용 | 검증된 컴포넌트, 상태관리 재사용 | "OMR 느낌"은 결국 직접 스타일링해야 해서 이점이 제한적 |

**채택**: 순수 CSS Grid/Flexbox.

## 3. 응시 중 상태관리 (답안/타이머)

PRD에 이미 "새로고침/이탈 시 localStorage 임시저장"이 확정되어 있음.

| 옵션 | 장점 | 단점 |
|---|---|---|
| **클라이언트 localStorage만 (채택)** | 인증 없는 구조와 가장 자연스럽게 맞음, 구현 단순 | 기기를 바꾸면 진행상황 유지 안 됨 (회차 타이머 응시 특성상 문제 안 됨) |
| 서버 세션(익명) + localStorage 병행 | 그룹 리더보드(Approach C) 확장 시 재설계 부담이 적음 | 지금 스코프엔 서버 구축이 과함, "가볍게" 제약과 충돌 |

**채택**: 클라이언트 localStorage만. **트레이드오프 인지**: PRD Open Questions에 이미 명시된 대로, 그룹 리더보드(Approach C)를 실제로 만들게 되면 이 부분은 서버 구조로 재설계가 필요하다 — 지금은 의도적으로 그 비용을 나중으로 미루는 선택.

## 4. 자격증별 시험 규격 메타데이터 위치

| 옵션 | 장점 | 단점 |
|---|---|---|
| **자격증별 `meta.json` 파일 (채택)** | 지금의 `data/exam-questions/{자격증명}/{날짜}/` 파일 기반 구조와 자연스럽게 연결. 새 자격증 추가 시 파일 하나만 더하면 됨 | 자격증 수가 매우 많아지면 조회 성능 고려 필요 (지금 스코프엔 해당 없음) |
| 코드에 hardcode | 지금 당장은 더 빠름 | 자격증이 늘어날수록(이미 2개→더 늘 예정) 코드 수정이 반복되는 기술부채 |

**채택**: `data/exam-questions/{자격증명}/meta.json`.
